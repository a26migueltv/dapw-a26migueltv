## Exercicio 1: Resolución de nomes con dig

Nesta parte utilizouse a ferramenta `dig` para resolver distintos dominios. Non se indicou ningún servidor, así que as consultas van ao servidor DNS que ten configurado o equipo.

### 1.1 Resolución de www.google.com

Resolveuse o nome `www.google.com`. Na sección `ANSWER` aparecen varios rexistros **A**, cada un cunha IP distinta de Google, para repartir a carga entre varios servidores:

```bash
dig www.google.com
```

> Partes máis importantes da saída de `dig`:
>
> - `status`: resultado da consulta (`NOERROR` = correcta, `NXDOMAIN` = o nome non existe).
> - `flags`: `qr` indica que é unha resposta, `rd` que se pediu recursión, `ra` que o servidor a admite e `aa` que a resposta é autoritativa.
> - `QUESTION SECTION`: o que se preguntou (nome e tipo de rexistro).
> - `ANSWER SECTION`: a resposta, co formato `nome  TTL  clase  tipo  valor`. O TTL son os segundos que se pode gardar en caché.
> - `SERVER`: IP, porto e protocolo do servidor DNS que respondeu.

## Exercicio 2: Servidor DNS propio con Docker

### 2.1 Posta en marcha do servidor

Como non se puido descargar o ficheiro `docker-compose.yaml`, creouse a man nun directorio novo co contido proporcionado e, dende ese directorio, levantouse o servidor DNS:

```bash
docker compose up
```

A interface web de administración está en `http://localhost:5380`. Accedeuse co usuario `admin` e o contrasinal `abc123.`.

O servidor DNS escoita no **porto 1053**, porque nos equipos da aula o porto 53 está ocupado. Por iso tódolos comandos `dig` contra este servidor levan a opción `-p 1053`.

> Para parar o servidor: `Ctrl + C` e despois `docker compose down`. Para continuar, volver executar `docker compose up`. Sempre dende o directorio do `docker-compose.yaml`.

### 2.2 Resolución de www.google.com co noso servidor

Coa opción `@localhost` a consulta vai ao servidor DNS levantado con Docker en lugar de ao que ten configurado o equipo:

```bash
dig @localhost -p 1053 www.google.com
```

Na liña `SERVER` aparece agora `localhost` co porto `1053`.

> O noso servidor non é **autoritativo** da zona `google.com`, así que fixo unha **consulta recursiva**: preguntou a outros servidores DNS ata obter a resposta. Por iso nos flags non aparece `aa`.

### 2.4 Rexistros A

Dentro da zona, con **Add Record**, creáronse tres rexistros de tipo **A**, que asocian un nome a unha IPv4:

| Nome           | IP           |
| -------------- | ------------ |
| `www.mtv.gal`  | `10.0.0.101` |
| `db.mtv.gal`   | `10.0.0.102` |
| `sftp.mtv.gal` | `10.0.0.103` |

> No campo do nome só se escribe a parte da esquerda (`www`, `db`, `sftp`); o servidor engade `.mtv.gal`.

Comprobouse cada un con `dig`:

```bash
dig @localhost -p 1053 www.mtv.gal
dig @localhost -p 1053 db.mtv.gal
dig @localhost -p 1053 sftp.mtv.gal
```

Agora nos flags aparece `aa`, xa que a resposta é **autoritativa**: a zona pertence ao noso servidor.

### 2.5 Rexistros CNAME para api e dashboard

A web está nun servidor coa IP `10.0.0.101` (`www.mtv.gal`), e no mesmo servidor tamén están `api.mtv.gal` e `dashboard.mtv.gal`. Se se usasen rexistros A, ao migrar o servidor habería que cambiar a IP nos tres. Por iso creáronse dous rexistros **CNAME** que apuntan a `www.mtv.gal`: así só hai que cambiar a IP nun sitio.

| Nome                | Tipo  | Apunta a      |
| ------------------- | ----- | ------------- |
| `api.mtv.gal`       | CNAME | `www.mtv.gal` |
| `dashboard.mtv.gal` | CNAME | `www.mtv.gal` |

```bash
dig @localhost -p 1053 api.mtv.gal
dig @localhost -p 1053 dashboard.mtv.gal
```

Na sección `ANSWER` aparece o CNAME cara `www.mtv.gal` e despois o rexistro A coa IP `10.0.0.101`.

### 2.7 Rexistro ANAME no ápice

Para que `mtv.gal` leve á mesma web que `www.mtv.gal` non se pode usar un CNAME. Un nome con CNAME non pode ter ningún outro rexistro, e o ápice sempre ten obrigatoriamente os rexistros SOA e NS.

Por iso creouse un rexistro **ANAME** co nome `@` (que representa o nome da zona, `mtv.gal`) apuntando a `www.mtv.gal`.

> Funcionamento do ANAME (noutros provedores ALIAS ou CNAME flattening):
>
> - Configúrase igual que un CNAME: `mtv.gal` → `www.mtv.gal`.
> - Cando chega unha consulta, o propio servidor resolve `www.mtv.gal` e devolve directamente os rexistros A.
> - O cliente recibe un rexistro A normal, polo que non hai conflito co SOA e o NS.
> - Se cambia a IP de `www.mtv.gal`, `mtv.gal` actualízase automaticamente.

```bash
dig @localhost -p 1053 mtv.gal
```

Agora a resposta é un rexistro **A** `mtv.gal → 10.0.0.101`, sen ningún CNAME.

### 2.8 Rexistro TXT

Ao despregar unha web, o provedor de certificados HTTPS (por exemplo Let's Encrypt) pode pedir engadir un rexistro **TXT** cun valor concreto para comprobar que somos donos do dominio. Unha vez verificado, emite o certificado.

Engadiuse un rexistro TXT co nome `_acme-challenge.www.mtv.gal` e o valor `x8FsezU9-8FwGz3gABX6JcRQ8hX8K4sNzyEaD9xRZpA`.

Para consultar este tipo de rexistro hai que indicalo no comando, porque por defecto `dig` pregunta polo rexistro A:

```bash
dig @localhost -p 1053 TXT _acme-challenge.www.mtv.gal
```

### 2.9 CNAME cara outra zona

Un CNAME tamén pode apuntar a un nome doutra zona. É habitual nos servizos cloud: a máquina virtual identifícase cun nome en lugar dunha IP (pola falta de IPs públicas), e apúntase a ese nome cun CNAME.

Creouse un rexistro CNAME para `search.mtv.gal` que apunta a `www.google.com`:

```bash
dig @localhost -p 1053 search.mtv.gal
```

Na resposta aparece o CNAME cara `www.google.com` e despois o rexistro A de Google, que o noso servidor obtivo de forma recursiva.
